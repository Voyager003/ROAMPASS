# roampass — Working Rules (CLAUDE.md)

Working rules for the **frontend (Next.js) repository** of the ZIVO USIM/eSIM take-home assignment. This is the reference whenever Claude and the user work together.
This file is adapted from `ROAMPASS_SERVER/CLAUDE.md`. The two repositories share the same principles, workflow, and commit convention so that the submission reads as one project.
If a rule conflicts with the assignment PDF, the assignment wins and this document gets fixed. The task checklist lives in `docs/plan.md`. `README.md` is a submission deliverable and contains only the items required by assignment §2.5.

---

## 0. Top Principles

1. **Meeting the six mandatory requirements in assignment §2.3 comes first.** The frontend owns §2.3-⑥ (user screens) and the screen half of §2.3-⑤ (admin). Bonus items, visual polish, and refactoring come after.
2. **Explainability over completeness.** Do not add code the user cannot explain in the second-round interview. For unfamiliar APIs or libraries, record the "why" in the commit body and in `docs/decisions.md`.
3. **Record the "why" on the spot.** README Q1 (why these technologies) and Q6 (server/client boundary, how the issuance-waiting screen refreshes) are written as the work happens, not at the end.
4. **Never commit secrets.** The backend URL and any keys live in `.env.local` (gitignored). `.env.example` holds the key names with dummy values.
5. **When something is unclear, write down an assumption and keep going.** Record it in the README "Assumptions" section.
6. **UI polish is explicitly not graded (§2.7).** What is graded is *how the screens are built in Next.js*: server/client boundary, how the issuance-waiting screen refreshes, and why App Router. Spend time there.

Evaluation weights (§2.7): Understanding & explanation 30% / Payment & issuance correctness 25% / Rationale for technical choices 15% / Requirement coverage 15% / Tests 10% / Deployment & reproducibility 5%
Drop order when short on time (§2.10): UI (6) → Orders (1) → Install tracking (4) → Admin (5) → Issuance (3) → Payment (2). Within the frontend, the admin screens outrank the user screens because the admin half of §2.3-⑤ is dropped later than §2.3-⑥.

## 1. Architecture

### Fixed decisions (see `docs/decisions.md` for the reasoning)
- **Next.js 16 App Router, Cache Components enabled** (`cacheComponents: true`, as generated by `create-next-app`).
- **One app holds both the user screens and the admin screens.** One deployment, one URL, shared API client and status labels.
- **BFF boundary: only the Next.js server talks to the Spring backend.** The browser never calls Spring directly.
  - Reads: Server Components. Anything uncached or request-dependent is wrapped in `<Suspense>`.
  - Writes: Server Actions (`'use server'`), which call the backend and then `refresh()` / `redirect()`.
  - Identity: **no login** (assignment §2.2: no member system, header-level identity is enough, do not spend time here). User screens act as `user-1` and admin screens as `admin-1` by default; an identity chip switches to `user-2` / `admin-2` (to demo "another user's order is 404" and "two operators click at once"). The choice lives in an httpOnly cookie that only the server reads (`lib/auth`, missing cookie → default, values outside the fixed list are ignored) and turns into `X-User-Id` / `X-Admin-Id` on backend calls (`docs/decisions.md` #4). No `/login` page, no `proxy.ts`.
  - The backend client module imports `server-only`. The backend URL is `BACKEND_URL` (never `NEXT_PUBLIC_`).
- **Issuance-waiting screen refreshes by polling with `router.refresh()`** from a small Client Component (`<Poller>`), using the backend's `waiting.pollIntervalSeconds` as the base interval; paused while the tab is hidden; stopped on a terminal order state. Exact interval/cap rules are decided in F1-5. No SSE, no client-side fetch of JSON.
- **Idempotency key only for order creation** (`docs/decisions.md` #6). The key is created once when the order form renders (Server Component, `crypto.randomUUID()`), carried in a hidden input, and sent by the Server Action as the `Idempotency-Key` header. Never create it inside the action on submit (a resubmit would get a new key). Payment, refund and operator actions send no key: the backend makes its own keys and answers repeats with 409 (`PAYMENT_IN_PROGRESS`, `REFUND_CONFLICT`, `ACTION_CONFLICT`), which screens show as "already in progress". Buttons are disabled while an action is pending; the server is what guarantees once-only execution.
- **User screens follow the provided demo video's purchase-screen layout** (`docs/decisions.md` #32–#38): bottom tab bar (홈 · 내 SIM), screen header (back · title · home), section titles with a blue left bar, cards on a grey basement, black selected chips, a collapsible user guide (warning Callout + tabs), an option summary, and a fixed bottom CTA. Built only with SEED components and our tokens; never copy the video's brand assets (logo, photos, illustrations, settings screenshots) or its out-of-scope features. Admin screens keep the wide desktop layout.
- **Admin screens do not auto-refresh.** Every admin page shows "N초 전 데이터" from the backend's `asOf` plus a refresh button.
- **Time is always displayed in KST** via `Intl.DateTimeFormat(..., { timeZone: 'Asia/Seoul' })` because the hosting runtime is UTC. Expiry is computed by the backend; the frontend only displays it.
- **Caching:** only the plan list uses `'use cache'` + `cacheLife`. Orders, payments, issuance, and admin data are never cached.
- **No data-fetching or state-management library** (SWR / TanStack Query / Zustand …, `docs/decisions.md` #9). Reads are Server Components, writes are Server Actions, in-screen state is `useState`/`useActionState` in leaf Client Components (the configure screen keeps its selection in one `useState`, #37), list filters live in URL `searchParams`, identity in the cookie. The only polling spot is covered by `router.refresh()`.
- **Backend HTTP is the Next-extended server `fetch`**, not Axios (`docs/decisions.md` #31). One `request()` in `lib/api/http-client.ts` handles non-2xx → `ApiError`, JSON, headers and a 10 s timeout. The timeout `signal` turns off Next's GET memoization, so wrap a query in React `cache()` when one render needs the same data twice.
- **UI components: SEED Design** (`@seed-design/react` + `@seed-design/css`, Apache-2.0, by Karrot). Rules:
  - **Import flat names only** (`BadgeRoot`, `BottomSheetRoot`, `TextFieldInput`). Namespace imports (`Badge.Root`) build a namespace object with a helper that lives in a `"use client"` file, and the production build fails when a Server Component touches it.
  - SEED components already carry `"use client"`; render them directly from Server Components. Our own `'use client'` files are still only for our state/effects/browser APIs.
  - Never use Karrot brand resources or Karrot-specific components (logo, name, characters, `MannerTemp*`, etc.): they are excluded from the license (package NOTICE). The brand color is overridden to our blue in `app/globals.css`.
  - Our status → SEED tone mapping lives in `components/ui/badge.tsx`; screens use `components/status-badges.tsx`, never `BadgeRoot` with a status directly.
  - SEED has no table: admin tables use our `components/ui/table.tsx` styled with SEED tokens.
- **Styling:** Tailwind v4 utilities mapped onto SEED variables in `app/globals.css` (`text-fg`, `text-fg-muted`, `bg-layer`, `bg-basement`, `border-line`, `rounded-card`, …). Never raw palette classes (`zinc-500`) or hex values in components.
- **Font:** SEED's system font stack (`--seed-font-family`). No web font is bundled. Numbers people compare or copy (amounts, ICCID, order numbers) use `tabular-nums`.

### Directory structure
```
roampass/
├── app/                       # Routes only. Pages compose feature components; no business logic here
│   ├── (user)/                # / (country cards), /plans/[country] (configure & order), /orders/[orderNo] (pay → issuance waiting), /my/sims, /my/sims/[orderNo]
│   └── admin/                 # /admin/orders, /admin/orders/[orderNo], /admin/issues
├── features/                  # One folder per domain, mirroring the backend packages
│   ├── plan/                  # queries, components
│   ├── order/                 # queries, actions, components (payment, issuance waiting, Poller)
│   ├── sim/                   # my SIMs, QR reveal, USIM ICCID registration
│   └── admin/                 # order list/detail/issues, operator actions
├── lib/
│   ├── api/                   # client.ts (interface) + http-client.ts (server-only fetch to BACKEND_URL), types.ts mirroring the backend response records, errors.ts
│   ├── auth/                  # demo identity: cookie → default user-1/admin-1, fixed list only (server-only)
│   └── format/                # KST date formatting, money formatting, status labels
├── components/                # status-badges (status → label/tone), identity-chip (switch demo identity), user shell (bottom tab bar, screen header), admin shell
│   └── ui/                    # Thin wrappers on SEED tokens: Badge (→ SEED), Card, Table (SEED has none), SectionTitle (blue bar), ChoiceChips, BottomCta, EmptyState. Buttons, inputs, tabs, accordions, callouts come from SEED directly
├── app/(dev)/ui/              # Component gallery in every state — development only, 404 in production
├── docs/                      # plan.md, decisions.md
└── README.md                  # Submission deliverable (§2.5 only)
```

### Layer rules
- `app/` files are thin: read `params`/`searchParams`, wire `<Suspense>`, render feature components.
- `features/*/queries.ts` and `features/*/actions.ts` are the only places that call `lib/api`. Components receive data as props or render async Server Components from `queries.ts`.
- A file is a Client Component (`'use client'`) only if it needs state, effects, event handlers, or browser APIs. Keep Client Components as leaves. Record every `'use client'` boundary that is not obvious in `docs/decisions.md` — this is README Q6 material.
- Never import `lib/api/client.ts` or `lib/auth` from a Client Component. They are `server-only`. `lib/api/types.ts` has no runtime dependencies and may be imported anywhere (`import type` in Client Components).
- Status labels, colors, and KST formatting live in `lib/format`, shared by user and admin screens. No inline status-to-label mapping in components.
- Types in `lib/api/types.ts` mirror the backend contract. When the backend changes a field, the type changes first, then the compiler finds the screens.

### Next.js version rule
This project runs **Next.js 16.4.2**, which differs from training data. Before using any Next.js API, file convention, or config option, read the matching page in `node_modules/next/dist/docs/01-app/` and cite the file in the commit body or `docs/decisions.md` when it drove a decision. Known differences already confirmed: `middleware.ts` is now `proxy.ts`; Cache Components require `<Suspense>` around uncached reads; `refresh()` from `next/cache` is available in Server Actions.

## 3. Development Workflow: Phase Process

### Structure
Each Phase in `docs/plan.md` (F0, F1, …) is split into sub-steps (F1-1, F1-2, …).
**Each Phase is worked on in its own branch** (see "Branch Strategy" below).

### Branch Strategy (one branch per Phase)
- Branch name: `phase/f{N}-{short-name}` (e.g. `phase/f0-foundation`, `phase/f1-screens`, `phase/f2-deploy`).
- When a Phase starts, create its branch from the latest `main`. All sub-step commits of that Phase go to this branch only — never commit Phase work directly to `main`.
- A Phase branch is merged into `main` only when **all** of its sub-steps are done and `npm run lint && npx tsc --noEmit && npm test && npm run build` pass on the branch.
- **Merge through a GitHub pull request**, same as the backend repository (`docs/decisions.md` #11): the user pushes the Phase branch, creates the PR, and merges with **"Create a merge commit"** so the merge commit marks the Phase boundary in `git log --graph`. Claude only writes the PR title and body (title one line, body a `* 작업` list, no AI attribution) and never merges locally.
- After the merge, update the local `main` (`git switch main && git pull`) before creating the next Phase branch.
- Do not start the next Phase branch until the previous Phase is merged into `main`.
- No squash, no rebase of pushed history, no force-push. The assignment evaluates the order in which problems were solved through the commit history.
- Fixes found after a Phase is merged go in the Phase currently in progress (as a `fix:` commit on that branch), not as a commit directly on `main`.
- Push the Phase branch to `origin` at least at the end of each sub-step so work is not lost.

### Rules
1. **Plan**: At the start of a Phase, before writing any code, present the full list of sub-steps and their tasks and get the user's confirmation.
2. **Execute per sub-step**: write code (+ tests where the sub-step has pure logic) → validate together with the user (lint/type-check/build result, screen check in the browser, code review) → commit only after validation passes.
3. **Wait**: After each sub-step, **always stop and wait for the user's next instruction.**
4. **Never auto-proceed**: Do not move to the next sub-step without an explicit instruction.

```
git switch -c phase/f1-screens main
F1-1: code → [STOP] → user validation → wait for instruction → commit (on phase branch)
  ↓ "continue"
F1-2: code → [STOP] → user validation → wait for instruction → commit (on phase branch)
  ↓ ... all sub-steps done, checks green
[STOP] → Claude writes PR title/body → user pushes, opens the PR, merges with "Create a merge commit" → git switch main && git pull
```
Refactoring follows the same flow.

### Sub-step Completion Report Format
**1. Work done** — files created/modified/deleted, summary per file, check results (lint / tsc / build / tests), which screens and states were verified
**2. Rationale** — why this structure/pattern, which §2.3/§2.4 requirement it satisfies, and why alternatives were rejected (if any)
**3. Docs updated** — what was added to `docs/decisions.md` / README, checklist items ticked in `docs/plan.md`, and the proposed next sub-step

### Validation before every commit
- `npm run lint` passes, `npx tsc --noEmit` passes, `npm test` passes, `npm run build` passes.
- Screens are built against the backend contract (`lib/api/types.ts`, `docs/api-coverage.md`) in each sub-step. **Running them against the local backend happens once, in the final integration sub-step of the screens Phase** (`docs/decisions.md` #39): every row of `docs/api-coverage.md` and every state, using backend fault injection for failure states.
- No secrets in `git diff --cached`. `.env.local` is never staged.
- `docs/decisions.md` updated if a choice was made.

## 4. Tests

The assignment requires no frontend tests (§2.5-⑤ concerns the backend). Tests here exist only where logic is pure and a wrong answer would mislead a user:
- `lib/format`: KST formatting across the midnight boundary, status label mapping is exhaustive over the state enum
- ICCID client-side validation (length, Luhn) — mirrors the backend rule, never replaces it
- `<Poller>` interval/stop logic, if extracted as a pure schedule function

Tool: **Vitest 4.1** (`npm test`). Run date/time tests under more than one `TZ` when touching `lib/format/kst.ts` (e.g. `TZ=UTC npm test`, `TZ=America/Los_Angeles npm test`): the formatters must not depend on the process time zone. Test file next to the module: `kst.test.ts`. Names in English snake_case, `describe` in Korean. Forbidden: tests that verify nothing.

## 5. Commit Convention

- Messages are written in **Korean**, format `<type>: <description>` (scope optional: `feat(order): …` allowed)

| Type | Usage |
|---|---|
| `feat` | New screen, component, or behavior |
| `fix` | Bug fix |
| `refactor` | Structural change without behavior change |
| `style` | Visual-only change (Tailwind classes, layout) with no behavior change |
| `test` | Adding/modifying tests only |
| `chore` | Build, config, dependencies |
| `docs` | Documentation only |
| `merge` | (GitHub creates it: "Merge pull request #N …" when a Phase PR is merged) |

Examples
```
feat: 요금제 목록 화면 및 국가·일수·용량 필터 추가
feat(order): 발급 대기 화면 폴러 및 종료 상태 처리
fix: 만료 시각 KST 자정 경계 표시 오류 수정
style: 어드민 주문 목록 테이블 간격 정리
chore: Vitest 설정 및 lib/format 테스트 추가
docs: decisions.md에 폴링 선택 이유 기록
```
- Body (optional): one or two lines on why it was done this way and which alternatives were rejected. Required for commits that involve a design decision or a `'use client'` boundary.
- Commits go on the current Phase branch, never directly on `main`. `main` only receives merge commits of completed Phase PRs.
- Claude proposes a commit message draft and commits only after the user confirms. No trailers (Co-Authored-By, etc.).
- Commit unit = one problem solved. One screen or one component per commit is the usual size.

## 9. Things Claude Must Never Do

- Never call the Spring backend from the browser (no `fetch` to `BACKEND_URL` in a Client Component, no `NEXT_PUBLIC_BACKEND_URL`).
- Never read the identity cookie in the browser or pass IDs through the URL.
- Never guess a Next.js 16 API — read `node_modules/next/dist/docs` first.
- Never add a data-fetching library, state library, or another UI component library without a `docs/decisions.md` entry and user confirmation.
- Never import SEED components through namespaces (`Badge.Root`) — flat names only.
- Never move to the next sub-step without user confirmation.
- Never commit Phase work directly to `main`, and never merge a Phase branch locally (the user merges the PR on GitHub).
- Never commit with failing lint / type-check / build.
- Never hardcode secrets or the backend URL in source.
- Never put a status-to-label mapping inline in a component.
- Never start bonus work (en locale, multi-currency display) before the mandatory screens and the README answers are done.
- Never present seed or demo data as real data in the README or demo instructions.

Environment note: screens are verified in the user's browser against `npm run dev`.
Dependency changes: Claude's device shell is Linux while `node_modules` is the user's macOS install. Never run `npm install` in the project folder from that shell (it rewrites the hidden `node_modules/.package-lock.json` and macOS-only binaries). Generate `package.json` / `package-lock.json` in a temporary copy (`npm install --package-lock-only`), copy only those two files back, verify with `npm ci` in a clean environment, and ask the user to run `npm install` on the Mac. Every screen from F1 on requires the backend running locally (`ROAMPASS_SERVER` README) or the deployed backend URL.
