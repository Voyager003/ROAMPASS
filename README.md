# roampass

여행자용 유심(USIM)·이심(eSIM) 판매 서비스 **ROAMPASS**의 프론트엔드 (Next.js)
백엔드 저장소: `ROAMPASS_SERVER` (Spring)

---

## 1. 실행 방법

**필요 환경:** Node.js 20.9 이상(Next.js 16 최소 버전), npm 10 이상.

```bash
git clone <이 저장소 URL> roampass
cd roampass
npm ci
cp .env.example .env.local
npm run dev
```

브라우저에서 http://localhost:3000 을 엽니다. **로그인은 없습니다.**

| 역할 | 기본 신원 | 바꿀 수 있는 신원 | 들어가는 곳 |
|---|---|---|---|
| 사용자 | `user-1` | `user-2` | `/` (홈), `/my/sims` (내 SIM) |
| 운영자 | `admin-1` | `admin-2` | `/admin/orders` (주문), `/admin/issues` (이상 건) |

회원 시스템은 과제 범위 밖이라(과제 2.2) 처음부터 기본 신원으로 동작하고, 화면 위쪽의 신원 칩으로 바꿀 수 있습니다. 고른 값은 `httpOnly` 쿠키에 저장되고, Next.js 서버가 백엔드를 호출할 때 `X-User-Id` / `X-Admin-Id` 헤더로 바꿔 보냅니다.

**백엔드가 먼저 떠 있어야 합니다.** 화면의 모든 데이터는 Spring 백엔드(`ROAMPASS_SERVER`)에서 옵니다. 백엔드 README의 "로컬 실행"대로 PostgreSQL, `roampass-api`(8080), `mock-pg`(8081), `mock-supplier`(8082)를 띄운 뒤 이 앱을 실행합니다. 백엔드 주소가 다르면 `.env.local`의 `BACKEND_URL`을 바꿉니다. 백엔드에 닿지 않으면 화면에 "백엔드에 연결할 수 없음" 오류가 보입니다.

**그 밖의 명령**

```bash
npm test             # 단위 테스트 (Vitest)
npm run lint         # ESLint
npx tsc --noEmit     # 타입 검사 (처음이라면 먼저 `npx next typegen`으로 라우트 타입 생성)
npm run build        # 프로덕션 빌드
```

개발 서버에서는 http://localhost:3000/ui 에서 공통 컴포넌트를 모든 상태로 볼 수 있습니다(프로덕션에서는 404).

**환경 변수** (`.env.local`)

| 키 | 설명 |
|---|---|
| `BACKEND_URL` | Spring 백엔드 주소(기본 `http://localhost:8080`). Next.js 서버에서만 읽고 브라우저에는 노출하지 않음. 브라우저는 Next.js만 호출하므로 백엔드 CORS 설정과 무관 |

## 2. 질문에 대한 답

### 2.1 왜 이 기술들을 골랐습니까?

_(초안. 근거 원본은 `docs/decisions.md`의 번호)_

**Next.js 16 App Router + Cache Components** (#1)
- 과제가 Next.js를 지정했고, App Router를 택했습니다. 서버 컴포넌트로 "백엔드는 서버에서만 부른다"는 경계를 파일 단위로 드러낼 수 있어서, 설명과 코드가 일치합니다.
- Cache Components(`create-next-app` 기본값)는 캐시되지 않는 읽기를 `<Suspense>`로 감싸게 강제합니다. 그래서 무엇이 요청 시점 데이터인지 코드에 드러납니다. 빌드 결과에서도 쿠키를 읽는 화면이 정적 셸 + 스트리밍(Partial Prerender)으로 나오는 것을 확인했습니다.
- 버린 선택지: Pages Router. 서버/클라이언트 경계를 `getServerSideProps`와 API 라우트로 나눠야 해서 경계가 코드에 덜 드러납니다.

**사용자 화면과 어드민을 한 앱에** (#2)
- 배포와 URL이 하나로 끝나고, API 클라이언트·상태 라벨·KST 포맷을 공유합니다.
- 버린 선택지: 앱 2개. 공유 코드를 복사하거나 패키지로 빼야 합니다.

**BFF: 백엔드는 Next.js 서버만 호출** (#3, #4)
- 조회는 서버 컴포넌트, 변경은 Server Action이 백엔드를 부릅니다. 브라우저는 백엔드 주소를 모릅니다.
- 얻는 것: CORS 설정이 필요 없고, HTTP만 열린 백엔드도 HTTPS 프론트에서 부를 수 있으며, 신원 헤더가 브라우저에 노출되지 않습니다.
- 대가: 모든 요청이 Next.js 서버를 한 번 더 거칩니다.
- 신원은 로그인 없이 기본 데모 신원(`user-1`·`admin-1`)으로 동작하고, 신원 칩으로 바꾼 값은 `httpOnly` 쿠키에 두어 서버만 읽습니다.

**백엔드 호출은 Axios 대신 서버 `fetch`** (#31)
- Next.js가 서버 `fetch`를 캐시·메모이제이션과 함께 확장하는 기본 경로로 둡니다. 호출 지점이 한 파일뿐이라 오류 변환·JSON·헤더·타임아웃은 함수 하나로 충분했습니다.
- 대가: 10초 타임아웃을 거는 `signal` 때문에 Next의 GET 메모이제이션이 꺼집니다. 같은 렌더에서 같은 데이터가 두 번 필요하면 React `cache()`로 보완합니다.

**데이터 패칭·상태 관리 라이브러리를 쓰지 않음** (#9, #37)
- 서버 데이터는 서버 컴포넌트가 매 요청 읽어 렌더하므로 클라이언트 캐시가 없습니다. 화면 사이에서 공유되는 클라이언트 상태도 없습니다(주문은 서버, 목록 필터는 URL, 신원은 쿠키). 구성 화면의 선택은 클라이언트 컴포넌트 하나의 `useState`입니다.

**발급 대기 화면은 `router.refresh()` 폴링** (#5, #13)
- 백엔드가 DB 상태 기반 스케줄러로 발급을 처리해서 서버가 밀어줄 이벤트 채널이 없습니다. SSE로 가면 서버 안에서 DB를 폴링하게 되고, 1GB 인스턴스에 연결을 붙잡아 둡니다.
- `router.refresh()`는 서버 컴포넌트를 다시 그리면서 클라이언트 상태는 유지하므로, 상태를 표시하는 코드가 서버 렌더 한 곳에만 있습니다. 간격은 백엔드가 주는 권장 값(`waiting.pollIntervalSeconds`)을 씁니다.

**멱등 키는 주문 생성에만** (#6)
- 주문 폼을 렌더할 때 키를 만들어 두므로, 응답이 유실된 뒤 다시 제출해도 같은 주문이 돌아옵니다. 결제·환불·운영자 조치는 대상 주문이 있어 백엔드가 상태 규칙(409)으로 중복을 막습니다.

**UI는 당근 SEED Design** (#18~#21)
- 버튼·입력·탭·아코디언 같은 모바일 구매 화면 부품을 직접 만들지 않고 공개 디자인 시스템을 썼습니다.
- 토스 TDS도 검토했지만 앱인토스 전용 라이선스라 외부 프로젝트에서 쓸 수 없었습니다. SEED는 코드가 Apache-2.0입니다. 당근 브랜드 리소스는 라이선스에서 제외되므로 쓰지 않았고, 강조색도 우리 색으로 바꿨습니다.
- 대가: 의존 패키지가 약 70개 늘었고, 표 컴포넌트가 없어 어드민 표는 직접 만들었습니다.
- 사용자 화면 구성은 제공받은 실제 서비스 시연 영상의 구매 화면을 따랐습니다(#32~#38). 브랜드 이미지·문구는 쓰지 않았습니다.

**시각은 항상 KST를 명시** (#8, #14)
- 배포 런타임(Vercel)은 UTC이고 운영 기준은 KST입니다. 모든 시각 포맷에 `timeZone: 'Asia/Seoul'`을 명시하고, 같은 테스트를 `TZ=UTC`·`America/Los_Angeles`·`Asia/Seoul`에서 돌려 결과가 같음을 확인합니다. 만료일 계산은 백엔드가 하고 프론트는 표시만 합니다.

**테스트는 Vitest 4.1** (#15)
- Vitest 5는 `@types/node` 22 이상을 요구해 `create-next-app`이 넣은 `^20`과 충돌합니다. 그래서 Node 20 타입을 허용하는 4.1 유지보수 라인을 택했습니다.
- npm 10에서 vitest의 peer인 vite가 8로 풀리면 순환 peer 때문에 설치가 실패해서, `overrides`로 vite를 7.3.7에 고정했습니다.

### 2.7 이번 과제에서 처음 써본 것이 있습니까?

_(초안 메모. 본인 경험 기준으로 확인·수정 필요)_

- **Next.js 16의 바뀐 규칙.** 학습 자료와 버전이 달라서, 코드를 쓰기 전에 설치된 패키지의 문서(`node_modules/next/dist/docs/`)를 먼저 읽었습니다. 예: Cache Components에서 요청 시점 데이터는 `<Suspense>` 안에서 읽어야 한다는 점, 서버 `fetch`에 `signal`을 주면 메모이제이션이 꺼진다는 점(Next 소스에서 확인).
- **SEED Design을 Next.js 서버 컴포넌트에서 쓰기.** 공식 예제처럼 `Badge.Root` 형태로 쓰면 개발 서버에서는 보이는데 프로덕션 빌드가 `__exportAll() ... is on the client` 오류로 실패했습니다. 빌드 결과물을 살펴보니, 묶음 객체를 만드는 헬퍼가 `"use client"` 파일 안에 있어 서버에서 호출할 수 없는 구조였습니다. `BadgeRoot`처럼 이름을 풀어 쓰는 방식으로 바꾸고, 이 규칙을 작업 규칙에 적었습니다.
- **AI가 틀린 것을 잡아낸 순간.**
  - 국가명 표시 테스트에서 `ZZ`를 "이름 없는 코드"로 가정했지만, 실제로는 국제 표준(CLDR)에 "알 수 없는 지역"이라는 이름이 있어 테스트가 실패했습니다. 코드를 `fallback: 'code'`로 고치고 테스트 값을 바꿨습니다.
  - Vitest 설치가 npm 10에서 실패했을 때, 처음에는 Vitest 5의 버전 문제로 판단했습니다. 로그를 따라가 보니 실제 원인은 vite 8 → devtools → vitest 5로 이어지는 peer 순환이었고, `overrides`로 해결했습니다.

## 5. 아키텍처

_(라우트·화면이 채워지면 갱신)_

```
브라우저 ──(페이지 요청 / Server Action POST)──▶ Next.js 서버 ──(X-User-Id, X-Admin-Id, 주문 생성 Idempotency-Key)──▶ Spring 백엔드
              ▲                                      │
              └──── RSC 스트리밍 (router.refresh 폴링) ─┘
```

| 위치 | 역할 |
|---|---|
| `app/` | 라우트만. `(user)` 사용자 화면(홈·구성·주문·내 SIM), `admin` 운영자 화면 |
| `lib/api/` | 백엔드에 닿는 유일한 통로(`server-only` `fetch`), 백엔드 응답 그대로의 타입 |
| `lib/auth/` | 데모 신원: 쿠키 → 기본값 `user-1`/`admin-1`, 고정 목록만 허용 |
| `lib/format/` | KST·금액·상태 라벨 (서버·클라이언트 공용, 테스트 대상) |
| `components/` | 사용자 셸(하단 탭·화면 헤더), 어드민 셸, SEED 위의 얇은 래퍼(섹션 제목·선택 칩·하단 버튼·표·배지) |

## 6. 가정

- 회원 시스템 대신 데모 신원(헤더 값)을 쓰고, 헤더는 위조할 수 있다는 한계를 인지합니다(과제 2.2).
- 웹에서는 기기의 eSIM 지원 여부를 알 수 없어, 구매 화면은 "지원 기종인지 먼저 확인하세요"라고만 안내합니다.
