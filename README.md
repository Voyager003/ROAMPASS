# roampass

여행자용 유심(USIM)·이심(eSIM) 판매 서비스 **ROAMPASS**의 프론트엔드 (Next.js)
백엔드 저장소: `ROAMPASS_SERVER` (Spring)

---

## 1. 실행 방법

### 사전 요구사항
- Node.js 20.9 이상(Next.js 16 최소 버전), npm 10 이상
- Docker, Docker Compose v2 (백엔드 실행용)

### 로컬 실행

화면의 모든 데이터는 Spring 백엔드에서 오므로 **백엔드를 먼저 띄웁니다.**

```bash
# 1) 백엔드: PostgreSQL + roampass-api(8080) + mock-pg(8081) + mock-supplier(8082)
git clone https://github.com/Voyager003/ROAMPASS_SERVER.git
cd ROAMPASS_SERVER
cp .env.example .env
docker compose --profile app up -d --build
curl http://localhost:8080/actuator/health   # status가 UP이면 준비 완료
cd ..

# 2) 프론트엔드
git clone https://github.com/Voyager003/ROAMPASS.git
cd ROAMPASS
npm ci
cp .env.example .env.local
npm run dev
```

| 화면 | 주소 |
|---|---|
| 사용자 화면 | http://localhost:3000 |
| 운영자 화면 | http://localhost:3000/admin |

**로그인은 없습니다.** 회원 시스템은 과제 범위 밖이라(과제 2.2) 처음부터 기본 데모 신원으로 동작합니다. 화면 위쪽의 신원 칩으로 같은 역할 안에서 바꿀 수 있습니다.

| 역할 | 기본 신원 | 바꿀 수 있는 신원 |
|---|---|---|
| 사용자 | `user-1` | `user-2` |
| 운영자 | `admin-1` | `admin-2` |

고른 신원은 `httpOnly` 쿠키에 저장되고, Next.js 서버가 백엔드를 호출할 때 `X-User-Id` / `X-Admin-Id` 헤더로 바꿔 보냅니다. 백엔드에 닿지 않으면 화면에 "백엔드에 연결할 수 없음" 오류가 보입니다.

### 환경 변수 (`.env.local`)

| 키 | 설명 |
|---|---|
| `BACKEND_URL` | Spring 백엔드 주소(기본 `http://localhost:8080`). Next.js 서버에서만 읽고 브라우저에는 노출하지 않습니다. 브라우저는 Next.js만 호출하므로 백엔드 CORS 설정과 무관합니다 |

### 그 밖의 명령

```bash
npm test             # 단위 테스트 (Vitest)
npm run lint         # ESLint
npx next typegen     # 라우트 타입 생성 (타입 검사 전 최초 1회)
npx tsc --noEmit     # 타입 검사
npm run build        # 프로덕션 빌드 (백엔드 없이도 빌드됨)
npm start            # 빌드 결과 실행
```

개발 서버에서는 http://localhost:3000/ui 에서 공통 컴포넌트를 모든 상태로 볼 수 있습니다(프로덕션 빌드에서는 404).

## 2. 질문에 대한 답

### 2.1 왜 이 기술들을 골랐습니까?

근거 원본은 `docs/decisions.md`이고, 괄호 안 `#번호`가 그 결정입니다.

#### 2.1.1 Next.js: 라우터·데이터 패칭·상태 관리

**한 줄 요약:** App Router로 화면을 서버 컴포넌트 중심으로 만들고, 백엔드는 Next.js 서버만 부르게 했습니다(BFF). 읽기는 서버 컴포넌트, 쓰기는 Server Action, 화면 안의 상태는 잎(leaf) 클라이언트 컴포넌트의 `useState`와 props로 처리해서 데이터 패칭·상태 관리 라이브러리를 쓰지 않았습니다.

##### 라우터: App Router (#1, #2, #36)

App Router를 고른 이유는 **"백엔드는 서버에서만 부른다"는 경계를 파일 단위로 드러낼 수 있기 때문**입니다. 서버 컴포넌트가 기본이라 데이터를 읽는 코드는 브라우저 번들에 들어가지 않고, 브라우저에서 돌아야 하는 부분만 `'use client'` 파일로 분리됩니다. 그래서 2.6의 "서버와 클라이언트의 경계"를 설명할 때 코드의 파일 구조가 그대로 답이 됩니다.

- **버린 선택지, Pages Router:** 데이터 읽기를 `getServerSideProps`와 API 라우트로 나눠야 하고, 페이지 전체가 클라이언트 컴포넌트로 하이드레이션돼서 경계가 코드에 덜 드러납니다.
- **Cache Components(`cacheComponents: true`)를 켠 이유:** `create-next-app` 기본값이고, 캐시되지 않는 읽기를 `<Suspense>` 안에 두도록 강제합니다. 그래서 "무엇이 요청 시점 데이터인지"가 코드에 보이고, 빌드 결과에서도 쿠키를 읽는 화면이 정적 셸 + 스트리밍(Partial Prerender)으로 나옵니다.
- **사용자 화면과 운영자 화면을 한 앱에** 두고 라우트 그룹으로 나눴습니다. 배포·URL이 하나로 끝나고 API 클라이언트·상태 라벨·KST 표시 함수를 공유합니다.

| 라우트 | 화면 |
|---|---|
| `app/(user)/(tabs)/` | 홈 `/`(국가 카드), 내 SIM `/my/sims`. 하단 탭이 있는 화면 |
| `app/(user)/` | 구성·주문 `/plans/[country]`, 주문·결제·발급 대기 `/orders/[orderNo]`, 내 SIM 상세 `/my/sims/[orderNo]` |
| `app/admin/` | 주문 목록 `/admin/orders`, 주문 상세·조치 `/admin/orders/[orderNo]`, 처리 대기 `/admin/issues` |

`app/`의 파일은 얇게 두고(정적 헤더 + `<Suspense>` + 기능 컴포넌트), 실제 화면과 데이터 읽기·쓰기는 `features/{plan,order,sim,admin}`에 백엔드 패키지 단위로 모았습니다.

##### 데이터 패칭: 서버 컴포넌트에서 서버 `fetch`, 브라우저는 백엔드를 모름 (#3, #10, #30, #31, #40)

```
읽기: 페이지(서버) → features/*/queries.ts (server-only) → lib/api/http-client.ts fetch → Spring
쓰기: 폼 → Server Action (features/*/actions.ts) → 같은 http-client → Spring → refresh() / redirect()
```

- **BFF로 둔 이유:** 브라우저에서 백엔드를 직접 부르지 않으니 CORS 설정이 필요 없고, HTTP만 열린 백엔드도 HTTPS 프론트에서 혼합 콘텐츠 문제 없이 부를 수 있으며, 백엔드 주소와 신원 헤더가 브라우저에 노출되지 않습니다. 대가는 모든 요청이 Next.js 서버를 한 번 더 거친다는 것입니다.
- **클라이언트 패칭이 없습니다.** 모든 읽기는 서버 컴포넌트가 요청마다 하고, 결과를 HTML·RSC로 스트리밍합니다. 브라우저 쪽 코드는 데이터를 가져오지 않고 "언제 다시 그릴지"만 정합니다.
- **스트리밍:** 각 페이지는 정적 헤더를 먼저 보내고, 백엔드를 읽는 본문은 `<Suspense>` 안에서 스켈레톤 → 실제 내용으로 바뀝니다.
- **캐시는 요금제 목록 하나만** 씁니다. 모든 사용자에게 같고 자주 바뀌지 않아서 `'use cache'` + `cacheLife('hours')`로 둡니다. 그 앞에 `connection()`을 두어 빌드 때 백엔드를 부르지 않게 했습니다(백엔드 없이도 `npm run build`가 됨). 주문·결제·발급·어드민 데이터는 사용자별이고 수 초 단위로 바뀌므로 캐시하지 않습니다.
- **Axios 대신 서버 `fetch`:** Next.js가 확장한 기본 경로이고, 호출 지점이 `lib/api/http-client.ts`의 `request()` 하나라 오류 변환(`ProblemDetail` → `ApiError`)·JSON·헤더·타임아웃을 함수 하나로 처리할 수 있었습니다. 백엔드가 멈추면 렌더가 끝없이 기다리지 않도록 모든 요청에 10초 타임아웃을 겁니다. 이 `signal` 때문에 Next의 GET 중복 제거(메모이제이션)는 꺼지지만, 지금은 한 렌더에서 같은 API를 두 번 부르는 곳이 없어 따로 보완하지 않았습니다.
- **쓰기는 Server Action**입니다. 폼의 `action`에 넘기고 `useActionState`로 진행 중 표시와 결과 문구를 받습니다. 성공하면 `refresh()`로 서버 컴포넌트를 다시 그리거나 `redirect()`로 이동하고, 409(이미 처리됨)도 문구를 보여 준 뒤 `refresh()`로 최신 상태를 그립니다.

**화면이 바뀌어야 할 때 다시 읽는 방법**

| 상황 | 방법 | 이유 |
|---|---|---|
| 결제 후 발급 대기 (#5, #13, #42) | `<Poller>`가 `router.refresh()`를 백엔드가 준 간격(`waiting.pollIntervalSeconds`, 기본 3초)마다 호출. 탭이 숨겨지면 멈추고, 끝 상태가 되면 서버가 `<Poller>`를 그리지 않아 멈춤. 5분이 지나면 멈추고 새로고침 버튼 | 백엔드가 DB 상태 기반 스케줄러로 발급을 처리해 밀어줄 이벤트 채널이 없습니다. SSE로 가면 결국 서버 안에서 DB를 폴링하게 되고 1GB 인스턴스에 연결을 붙잡아 둡니다. `router.refresh()`는 서버 컴포넌트를 다시 그리면서 클라이언트 상태는 유지하므로, 상태를 표시하는 코드가 서버 렌더 한 곳에만 있습니다 |
| 결제 기한 카운트다운 (#47) | 클라이언트에서 1초마다 계산. 첫 렌더는 서버 시각(`serverNow`)으로 그리고 기기 시계 차이를 보정. 0초가 지나면 한 번 `refresh()` | 1초 표시에 서버 왕복이 필요 없습니다. 만료 판정은 백엔드가 합니다 |
| 운영자 화면 (#7) | 자동 갱신 없음. 백엔드 `asOf`로 "N초 전 데이터"를 보여 주고 새로고침 버튼(`router.refresh()`) | 조치 버튼을 누르는 화면이 몰래 바뀌면 판단이 흔들립니다. 데이터의 나이를 보여 주고 갱신은 운영자가 선택합니다 |

##### 상태 관리: 라이브러리 없이 "상태가 사는 곳"을 나눔 (#4, #9, #37)

Redux·Zustand 같은 상태 관리 라이브러리나 SWR·TanStack Query를 쓰지 않았습니다. **화면 사이에서 공유되는 클라이언트 상태가 없기 때문**입니다. 상태마다 가장 알맞은 곳에 두었습니다.

| 상태 | 사는 곳 | 이유 |
|---|---|---|
| 주문·결제·발급·설치 상태 | 백엔드 (서버 컴포넌트가 요청마다 읽음) | 진실은 백엔드에 있고, 결제 직후 브라우저를 닫아도 서버에서 끝까지 진행됩니다. 프론트가 복사본을 들고 있지 않습니다 |
| 운영자 목록의 필터·페이지 | URL `searchParams` (`<form method="get">`) | 새로고침·뒤로 가기·링크 공유에 그대로 남고, JS 없이 동작합니다 |
| 데모 신원 | `httpOnly` 쿠키 → 서버가 읽음 | 브라우저 JS가 신원을 읽거나 바꿀 수 없습니다 |
| 구성 화면의 선택(시작일·사용기간·데이터·SIM) | `PlanConfigurator` 하나의 `useState` | 칩을 누를 때마다 서버를 거치지 않고 즉시 좁혀야 합니다 |
| 폼 진행 중·결과 문구 | 각 폼의 `useActionState` | Server Action과 함께 쓰는 React 기본 훅입니다 |
| 시간이 흐르며 바뀌는 표시(카운트다운·남은 기간·N초 전) | 그 표시 컴포넌트의 `useState` + 타이머 | 서버 시각을 첫 값으로 받아 서버·브라우저 렌더가 같습니다 |

**props로 내려 주는 구조 (구성 화면):**

```
ConfigureScreen (서버 컴포넌트)
 ├ getPlans()로 요금제 목록, KST 오늘·1년 뒤, 주문 멱등 키(crypto.randomUUID)를 만듦
 └▶ PlanConfigurator (클라이언트) props: plans, today, maxDate, idempotencyKey, orderAction(Server Action)
     ├ useState: startDate, selection
     ├▶ TravelDateCalendar  props: value, onValueChange, min, max
     ├▶ ChoiceChips ×3      props: options(요금제에 존재하는 값만), value, onValueChange
     └ 요약·결제 버튼: 상태에 저장하지 않고 selection으로 매번 계산(resolvePlan)
```

- **상태는 한 곳(`PlanConfigurator`)에만 있고**, 하위 컴포넌트는 `value`/`onValueChange`를 받는 제어 컴포넌트입니다. 깊이가 한 단계라 Context가 필요 없습니다.
- **고른 요금제는 저장하지 않고 계산합니다.** 선택에서 요금제를 매번 도출하므로 두 상태가 어긋날 일이 없습니다. 좁히기 규칙은 순수 함수(`features/plan/selection.ts`)라 테스트로 고정했습니다.
- **서버 → 클라이언트로 넘기는 것은 직렬화 가능한 값과 Server Action뿐**입니다. 함수 중에서는 Server Action만 클라이언트 컴포넌트로 넘길 수 있어서, 주문 생성 액션을 props로 내려 줍니다.
- **멱등 키를 렌더 시점에 만드는 이유:** 응답이 유실돼 같은 폼을 다시 제출해도 같은 키가 가서 백엔드가 같은 주문을 돌려줍니다. 제출할 때마다 키를 만들면 재제출도 새 주문이 됩니다(#6).
- **대가:** 구성 화면을 새로고침하면 선택이 사라집니다. 고르는 과정이 짧고 "결제하러 가기" 순간 주문이 서버에 생기므로 받아들였습니다.

**우리가 만든 클라이언트 컴포넌트(14개)는 모두 잎입니다.** 브라우저만 아는 값이 필요한 곳에만 둡니다: 현재 경로(하단 탭·메뉴), 구성 화면의 선택·달력·칩, 폴러, 카운트다운·남은 기간·"N초 전" 표시, 각 폼(결제·환불·ICCID 등록·설치 코드 보기·운영자 조치·시연 버튼). 레이아웃, 데이터 읽기, 신원 표시는 모두 서버 컴포넌트입니다. SEED 컴포넌트는 패키지 안에 `"use client"`가 있어 서버 컴포넌트에서 그대로 렌더합니다.

#### 2.1.2 그 밖의 선택

**UI는 당근 SEED Design** (#18~#21)
- 버튼·입력·탭·아코디언 같은 모바일 구매 화면 부품을 직접 만들지 않고 공개 디자인 시스템을 썼습니다.
- 토스 TDS도 검토했지만 앱인토스 전용 라이선스라 외부 프로젝트에서 쓸 수 없었습니다. SEED는 코드가 Apache-2.0입니다. 당근 브랜드 리소스는 라이선스에서 제외되므로 쓰지 않았고, 강조색도 우리 색으로 바꿨습니다.
- 대가: 의존 패키지가 약 70개 늘었고, 표 컴포넌트가 없어 어드민 표는 직접 만들었습니다.
- 사용자 화면 구성은 제공받은 실제 서비스 시연 영상의 구매 화면을 따랐습니다(#32~#38). 브랜드 이미지·문구는 쓰지 않았습니다.

**시각은 항상 KST를 명시** (#8, #14)
- 배포 런타임(Vercel)은 UTC이고 운영 기준은 KST입니다. 모든 시각 포맷에 `timeZone: 'Asia/Seoul'`을 명시하고, 같은 테스트를 `TZ=UTC`·`America/Los_Angeles`·`Asia/Seoul`에서 돌려 결과가 같음을 확인합니다. 만료일 계산은 백엔드가 하고 프론트는 표시만 합니다.

**테스트는 Vitest 4.1** (#15)
- Vitest 5는 `@types/node` 22 이상을 요구해 `create-next-app`이 넣은 `^20`과 충돌합니다. 그래서 Node 20 타입을 허용하는 4.1 유지보수 라인을 택했습니다.
- npm 10에서 vitest의 peer인 vite가 8로 풀리면 순환 peer 때문에 설치가 실패해서, `overrides`로 vite를 7.3.7에 고정했습니다.

**배포는 Vercel 무료 티어** (#12) — 이유는 [4. 배포](#4-배포)에 적었습니다.

- **Next.js 16의 바뀐 규칙.** 학습 자료와 버전이 달라서, 코드를 쓰기 전에 설치된 패키지의 문서(`node_modules/next/dist/docs/`)를 먼저 읽었습니다. 예: Cache Components에서 요청 시점 데이터는 `<Suspense>` 안에서 읽어야 한다는 점, 서버 `fetch`에 `signal`을 주면 메모이제이션이 꺼진다는 점(Next 소스에서 확인).

- **AI가 틀린 것을 잡아낸 순간.**
  - 국가명 표시 테스트에서 `ZZ`를 "이름 없는 코드"로 가정했지만, 실제로는 국제 표준(CLDR)에 "알 수 없는 지역"이라는 이름이 있어 테스트가 실패했습니다. 코드를 `fallback: 'code'`로 고치고 테스트 값을 바꿨습니다.
  - Vitest 설치가 npm 10에서 실패했을 때, 처음에는 Vitest 5의 버전 문제로 판단했습니다. 로그를 따라가 보니 실제 원인은 vite 8 → devtools → vitest 5로 이어지는 peer 순환이었고, `overrides`로 해결했습니다.

## 4. 배포

| 항목 | 값 |
|---|---|
| 프론트엔드 | Vercel (무료 Hobby 티어) — URL: _(배포 후 기입)_ |
| 백엔드 | Oracle Cloud 무료 인스턴스 2대 + Docker (백엔드 README 참고) |
| Vercel 환경 변수 | `BACKEND_URL` = 배포된 백엔드 주소 |

### Vercel을 고른 이유

1. **이 프로젝트가 쓰는 Next.js 16 기능이 검증된 플랫폼입니다.** 이 앱은 서버 컴포넌트, Partial Prerendering(정적 셸 + 스트리밍), Cache Components(`'use cache'`), Server Actions를 씁니다. Next.js 배포 문서(`node_modules/next/dist/docs/01-app/02-guides/deploying-to-platforms.md`)는 이 기능들이 모두 **스트리밍 응답을 지원하는 플랫폼**을 필요로 한다고 적고 있습니다. 같은 문서(`01-getting-started/17-deploying.md`)의 **검증된 어댑터(verified adapter)** 목록에는 Vercel만 있고, Cloudflare·Netlify는 아직 준비 중이라 기능 지원이 다를 수 있다고 합니다. 기능이 동작하는지 직접 확인하는 데 시간을 쓰지 않으려고 검증된 쪽을 골랐습니다.
2. **무료 티어로 충분합니다.** 과제가 "무료 티어로 충분하고 과금되는 선택은 하지 말 것"이라고 했고, 이 앱은 트래픽이 거의 없는 시연용입니다.
3. **백엔드 인스턴스에 프론트를 같이 올리지 않기 위해서입니다.** 백엔드는 1GB 인스턴스 2대에 API·DB·모의 서버를 나눠 올려 메모리 여유가 거의 없습니다. 여기에 Node.js 서버를 더 올리면 메모리가 부족해질 위험이 있어 프론트는 따로 분리했습니다.
4. **BFF 구조와 잘 맞습니다.** 브라우저는 HTTPS인 Vercel만 호출하고, 백엔드 호출은 Vercel의 서버에서 일어납니다. 그래서 백엔드가 HTTPS 인증서 없이 HTTP로만 열려 있어도 브라우저에서 혼합 콘텐츠 문제가 생기지 않고, 백엔드에 프론트 주소용 CORS 설정도 필요 없습니다.
5. **GitHub 저장소를 연결하면 push마다 자동으로 빌드·배포**되어 별도 배포 파이프라인을 만들지 않아도 됩니다.

**버린 선택지**
- **백엔드와 같은 Oracle 인스턴스에 Docker로 띄우기:** 3번의 메모리 문제가 있습니다.
- **Cloudflare Pages, Netlify:** 무료이고 Next.js를 지원하지만, 위 문서 기준으로 아직 검증된 어댑터가 아니라 Cache Components·PPR 동작을 직접 확인해야 했습니다.

**대가와 대응**
- **서버 런타임이 UTC입니다.** 운영 기준은 KST라, 모든 시각 표시에 `timeZone: 'Asia/Seoul'`을 명시하고 테스트를 세 시간대에서 돌려 확인합니다(#8, #14).
- **서버리스라 인스턴스마다 메모리 캐시가 따로입니다.** 요금제 목록 캐시가 인스턴스마다 한 번씩 백엔드를 다시 읽을 수 있습니다. 요금제는 자주 바뀌지 않아 받아들였습니다(#40).
- **요청마다 Vercel → Oracle 왕복이 한 번 더 생깁니다**(BFF의 대가). 함수가 실행되는 리전이 백엔드와 멀면 지연이 커집니다.

## 5. 아키텍처

_(라우트·화면이 채워지면 갱신)_

```
브라우저 ──(페이지 요청 / Server Action POST)──▶ Next.js 서버 ──(X-User-Id, X-Admin-Id, 주문 생성 Idempotency-Key)──▶ Spring 백엔드
              ▲                                      │
              └──── RSC 스트리밍 (router.refresh 폴링) ─┘
```

| 위치 | 역할 |
|---|---|
| `app/` | 라우트만. `(user)` 사용자 화면(홈·구성·주문·내 SIM), `admin` 운영자 화면 |
| `lib/api/` | 백엔드에 닿는 유일한 통로(`server-only` `fetch`), 백엔드 응답 그대로의 타입 |
| `lib/auth/` | 데모 신원: 쿠키 → 기본값 `user-1`/`admin-1`, 고정 목록만 허용 |
| `lib/format/` | KST·금액·상태 라벨 (서버·클라이언트 공용, 테스트 대상) |
| `components/` | 사용자 셸(하단 탭·화면 헤더), 어드민 셸, SEED 위의 얇은 래퍼(섹션 제목·선택 칩·하단 버튼·표·배지) |

## 8. 실제 투입 시간 · AI 도구 사용처
